The one that matters

Everything else in this report can wait a week. This cannot.

Any note you have ever shared is likely public right now

Migration 02_add_all_features.sql gates share-based note reads on a session variable: sn.id = current_setting('app.share_id')::uuid. The live database does not have that clause. The schema dump committed in schemadump.md shows the policy as EXISTS (SELECT 1 FROM shared_notes sn WHERE sn.note_id = notes.id) — the share-id check is simply absent.

With that clause gone, the policy reads: if a row exists in shared_notes for this note, anyone may select it. Not "anyone with the link" — anyone. And shared_notes itself carries shared_notes_public_read USING (true), so the share IDs, note IDs and owner UUIDs are enumerable by an anonymous caller holding only the public anon key, which ships in your JavaScript bundle.

SEC-01Share-scoped note policy lost its share-id predicateRLS · notes

The full unauthenticated chain, using nothing but the public anon key:

# 1. enumerate every share that exists
GET /rest/v1/shared_notes?select=id,note_id,owner_id,allow_edit

# 2. read the note body — no share id supplied anywhere
GET /rest/v1/notes?id=eq.<note_id>&select=title,content

# 3. if allow_edit is true, overwrite it
PATCH /rest/v1/notes?id=eq.<note_id>  {"content": "..."}

Step 3 is real: notes_update_via_share lost the same predicate and keeps only AND sn.allow_edit. Every editable share is world-writable, and the app's own Realtime subscription in SharedNote.tsx:69 will push an attacker's edits straight into the owner's open tab.

CONFIRM WITH → AUDIT_VERIFY.sql block [1]. If using_expr has no current_setting, this is live.

Fix. The session-variable design cannot work over PostgREST anyway — nothing in the codebase ever calls set_config('app.share_id', …), and pooled connections would leak it if it did. Replace it with a predicate the client can actually satisfy:

DROP POLICY IF EXISTS notes_select_via_share ON public.notes;
DROP POLICY IF EXISTS notes_update_via_share ON public.notes;
DROP POLICY IF EXISTS shared_notes_public_read ON public.shared_notes;

-- the share id becomes the secret: you must already know it
CREATE POLICY shared_notes_read_by_id ON public.shared_notes
  FOR SELECT USING (true);   -- keep, but ALWAYS filter by id (see note)

The clean version is a SECURITY DEFINER function get_shared_note(p_share_id uuid) that takes the share id, looks up the note, and returns it — with REVOKE ALL ON public.shared_notes FROM anon, authenticated so the table can't be enumerated at all. SharedNote.tsx then calls that one RPC instead of two table reads.

SEC-02shared_notes is fully enumerable by anonymous callersRLS · shared_notes

FOR SELECT USING (true) with no role restriction. Even after SEC-01 is fixed, this leaks the complete share table: how many notes each user shares, which are editable, and every owner's auth.users.id. Those UUIDs are the input to SEC-03.

FIX: REVOKE ALL ON public.shared_notes FROM anon, authenticated; and read shares only through a definer function keyed by share id.
SEC-03get_calendar_events trusts a caller-supplied user idIDOR · SECURITY DEFINER

Declared SECURITY DEFINER, granted to authenticated, and takes p_user_id uuid which it uses directly in every WHERE clause. It never compares that argument to auth.uid(). Definer rights mean RLS is bypassed.

Any signed-up user who knows another user's UUID can read their tasks, note titles, birthdays, countdowns, media library, and subscription names and amounts — six tables in one call. Combined with SEC-02, the attacker doesn't even need to guess the UUID. 

CREATE OR REPLACE FUNCTION public.get_calendar_events(...)
 LANGUAGE plpgsql SECURITY DEFINER      -- no SET search_path either
AS $function$
BEGIN
  ...  WHERE t.user_id = p_user_id;     -- caller-controlled, unchecked
FIX: add SET search_path = public and, as the first statement, IF p_user_id <> auth.uid() THEN RAISE EXCEPTION 'forbidden'; END IF; — or drop the parameter and use auth.uid() directly. useCalendar.ts:42 already passes the caller's own id, so dropping the parameter breaks nothing.
SEC-04get_upcoming_renewals has the same hole — and the migration doesn't say soIDOR · drift

Migration 02 creates this function as SECURITY INVOKER, which would be safe — RLS would filter it. The live function is SECURITY DEFINER with a different default (p_days DEFAULT 30 vs. 4). Someone redefined it in the dashboard and never wrote it back. Same fix as SEC-03.

CONFIRM WITH → block [3]. Look for mentions_auth_uid = false.
SEC-05media_metadata accepts writes from anyoneRLS · shared cache
CREATE POLICY "Allow service role insert" ON public.media_metadata
    FOR INSERT WITH CHECK (true);        -- applies to anon + authenticated
CREATE POLICY "Allow service role update" ON public.media_metadata
    FOR UPDATE USING (true);             -- no WITH CHECK at all

The policy names say "service role", but the service role bypasses RLS entirely — these policies exist only to grant anon and authenticated. This is a cross-tenant table with no user_id: anyone can rewrite every cover_image in your shared cache to a URL they control, giving them a request log of which titles your users browse, or insert rows until the table is a storage bill.

This is load-bearing, so it can't just be dropped: media-refresh.ts:347 and media-metadata.ts:469 both upsert here from the browser with the anon key. Route those writes through the edge function first, then restrict the policies to TO authenticated at minimum.

Check what's already in there → blocks [16] and [17]. Any host outside tmdb/anilist/mangadex/tvmaze/jikan/wikimedia is poisoning.
SEC-06The edge function is a public, unauthenticated service-role proxyedge function

deploy-edge-function.sh deploys with --no-verify-jwt, and the handler sets Access-Control-Allow-Origin: '*' while holding SUPABASE_SERVICE_ROLE_KEY. Four consequences, all reachable with curl:

  • Unauthenticated writes to media_metadata under service-role rights (index.ts:1199), amplifying SEC-05 past any RLS fix.
  • Free use of your TMDB quota as an open proxy.
  • details: error.message returned on 500 (index.ts:1220) — internal errors leak to callers.
  • limit is parseInt'd with no clamp, and handleBatchSearch feeds an unbounded items[] array straight into .in('title', titles). No rate limiting anywhere.
FIX: drop --no-verify-jwt and send the session token from the client; pin CORS to your own origin; clamp limit to 1–50 and items to ~50; return a generic 500 body.

What's built right

Worth naming, because the fixes above should not disturb any of it.

The Vault is the strongest thing in the codebase.

Private bucket, storage RLS keyed on the {user_id}/ path prefix, short-lived signed URLs minted per view, and no shareable link anywhere by design. uploadFile even removes the uploaded object if the metadata insert fails, so bytes are never orphaned. replaceFile rolls back the same way.

The avatars bucket excludes SVG.

allowed_mime_types is png/jpeg/webp/gif on a public bucket. Allowing image/svg+xml there would be stored XSS on your own origin. That's a subtle call, made correctly.

Every stored-HTML render path is sanitised.

Both dangerouslySetInnerHTML sites and all three innerHTML writes in SharedNote.tsx go through sanitizeHtml or sanitizePreview, with explicit allowlists and ALLOW_DATA_ATTR: false. This is what keeps SEC-01 from also being a stored-XSS vector.

Derived subscription charges instead of materialised rows.

deriveSubscriptionCharges computes each charge from start_date by billing cycle at read time. No background job, no drift, and editing or cancelling a subscription self-corrects retroactively. Migration 15's reasoning for the switch is genuinely well argued.

Migration 12 is a model postmortem.

It diagnoses "Database error saving new user" precisely — signup triggers running as supabase_auth_admin where auth.uid() is null, so RLS rejects the insert and rolls back the whole auth.users write — and fixes it with SECURITY DEFINER plus a pinned search_path. That pinning is exactly what SEC-08 is missing elsewhere.

Code splitting is real and measured.

Authenticated routes are lazy; manualChunks isolates the heavy leaves. CodeMirror (508 kB) and Recharts (400 kB) only download with the pages that use them, and the entry bundle is 175 kB. Hover-prefetch via route-prefetch.ts hides the latency.

Local-date discipline.

date-utils.ts exists specifically because toISOString().split('T')[0] silently shifts dates, and it's used consistently almost everywhere. BUG-15 is the one leak.

RLS is on every user table with the same predicate.

All 24 user-owned tables enable RLS and scope on auth.uid() = user_id, junction tables via an EXISTS against their parent. The critical findings above are three specific deviations from an otherwise uniform and correct model.

The comments explain why, not what.

Migration headers, vite.config.ts's chunking rationale, and the preferences.ts note about re-applying theme tokens all record reasoning a future reader would otherwise have to reconstruct. This is rarer than it should be.
